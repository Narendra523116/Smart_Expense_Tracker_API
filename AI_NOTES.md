# AI Tools Usage Notes

## Tools Used

- **Gemini** Used for  rate-limiting, middleware setup, Jest/Supertest test scaffolding.
- **Claude** Used for generating this `README.md` from the finished source code.

I treated both as a first-draft generator and pair-reviewer, not as an autopilot, every AI output below was read line-by-line against the running code before being kept.

---

## 1. Code Ownership Breakdown

### AI-generated, then reviewed and adapted

- **Rate limiting middleware** (`src/middlewares/rateLimiter.js`): AI drafted the two-tier limiter (100 reads / 15 min, 10 writes / 1 min) using `express-rate-limit`. I kept the structure but chose the actual thresholds myself based on what felt reasonable for a single-user demo API.
- **Integration test scaffolding** (`tests/expense.test.js`): AI generated the initial Jest + Supertest structure (describe/test blocks, request patterns). I rewrote the assertions to match my actual API contract (see corrections below) and added the negative-amount and 404 cases myself.
- **README.md**: Generated by AI directly from my final source code (routes, controllers, services, `package.json`), then manually verified, I ran `npm install`, `npm start`, and `npm test` on a clean checkout myself and corrected the parts that didn't match reality (see Section 3).

### Written / designed by me

- **Routing and controller logic** (`src/controllers/expenseController.js`): Response envelope (`{ message, data }`), input validation (`isNaN(amount)`, negative-amount rejection), and the custom `/delete/:id` route naming were my decisions, not AI's.
- **Data structure strategy** (`src/services/expenseServices.js`): I chose the in-memory `Map` + secondary category-index `Map` design specifically to keep lookups, category filtering, and totals at O(1), and implemented the three-step deletion (main map → category map → running totals) myself.
- **Error handling and status codes**: Standardized `400`/`404`/`500` responses across all four endpoints, written by hand, not AI-generated.

## 2. Validation, Testing & Corrections Made to AI Output

I didn't take any AI output at face value. Specific corrections:

| # | AI's first draft | What I found / changed | How I verified |
|---|---|---|---|
| 1 | Test suite asserted `GET /api/expenses` returns a top-level array `[...]` | My controller wraps every response in `{ message, data }` — a plain REST convention the AI defaulted to that doesn't match my actual envelope. Rewrote every test assertion to check `res.body.data` instead of `res.body`. | `npm test` — all 7 tests pass against the real envelope |
| 2 | Test suite (and README draft) assumed the standard REST path `DELETE /api/expenses/:id` | My actual route is the more explicit `DELETE /api/expenses/delete/:id`. Updated both the tests and the README endpoint table to the real path. | Confirmed against `src/routes/expenseRoutes.js` directly |
| 5 | AI's README draft assumed the server defaults to port `3000` | Actual fallback in `server.js` is `process.env.PORT \|\| 8080`, and the committed `.env` sets `PORT=5000`. Corrected the README to state the real default and the actual running port. | Ran `npm start` and read the printed `http://localhost:PORT` line |
| 6 | AI's README first draft listed `category` as case-sensitive in examples | Service layer lowercases category on every write and read (`category.toLowerCase()`), so filtering is case-insensitive. Corrected the README wording to reflect this. | Manually POSTed a mixed-case category and confirmed it round-trips lowercase |

## 3. AI Suggestions Rejected, and Why

1. **Persisting expenses to disk via `fs` on every write**  AI suggested writing to a local `expenses.json` file on every POST/DELETE for "durability." Rejected because synchronous/async file I/O adds latency and complexity that isn't justified for this project's scope; the in-memory `Map` design meets the requirements and keeps every operation O(1)
---

## Summary

AI was useful for scaffolding (middleware shape, test structure, and this README) and for surfacing ideas to react to, but the actual API contract, data-structure design, and error handling are mine, and every piece of AI output including this notes file's own claims — was checked against the running code rather than assumed correct.
